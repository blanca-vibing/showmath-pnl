产品案例展示

从 0 到 1 用 AI 搭建演出预算系统 · 一次失败的预测系统，如何转身成一个可用的损益工具

摘要

本案例记录了我如何在中国现场音乐行业里识别一个核心痛点，从一个走不通的机器学习构想果断 pivot，并在零工程团队的条件下，用 AI 工具搭出一个可用的巡演预算系统。系统覆盖 13 组 65 个成本项，内置 200+ 个场馆，并经过 16 份真实巡演 P&L 验证。它把巡演预算编制从 2–3 天压缩到约 2–3 小时——更重要的是，它让一些以前「做不到」的事变得可行：在几分钟内对比不同场馆组合、不同档期、不同票价策略下的利润结构。

一、问题与背景

The Pivot：从「票房预测」到「损益模拟」

这个项目最初叫「票房预测引擎」。想法很直接：用机器学习预测任意艺人在任意中国城市的售票情况，让公司在签约前就有数据驱动的判断力。我花了几周收集历史售票数据、做特征工程、搭原型。

两个问题让我停了下来。第一，数据根本不够——演出不像互联网产品每天产生上百万条日志，即使是国内最活跃的主办方，一年也就做十几场巡演，每场还高度依赖艺人类型、市场周期、营销投入等难以量化的变量。第二，也更关键：和团队聊过之后我意识到，没人需要一个模型来告诉他们能卖多少票——有经验的 PM 凭直觉就知道「这种艺人做 Livehouse，卖得完」。

真正的问题不是「能卖多少票」，而是「卖完之后，到底赚不赚钱？最多能给艺人报多少保底？换个场馆利润差多少？这站从周五改周六，多出来的场租换那 100 个观众值不值？」——这些问题，当时没有任何工具能快速回答。

于是我 pivot 了。不是跳到一个不相关的领域，而是在同一个大方向上，找到了痛点更精准的位置：从预测票房，转向模拟损益。这个 pivot 本身，是整段经历里最「产品经理」的一个决定。

真实痛点：为什么 Excel 不够用

在 Demo Live Entertainment 做巡演执行的两年多里，每做一次预算都像一次「考古」。一个 8 城巡演要查 8 个城市的场馆报价，每个场馆又分周五 / 周六 / 周日 / 工作日四档价格，散落在不同的 Excel 甚至去年的 PDF 里。成本项多达 65 项，每一项都要手动填。改一个变量——换场馆、把某站从周五挪到周六——整张预算几乎要重算一遍。

公司积累了 16 份历史巡演 P&L、300+ 场馆数据，但它们全都躺在不同人电脑里的孤立 Excel 文件中。每个新方案都得从头来过。海外有 Greencopper、Prism 这样的产品，但它们是为欧美市场设计的——场馆体系、成本结构（报批费、安保、中国票务平台费率）、运营流程完全不同。市面上没有一个适配中国的工具。

二、三个关键产品决策

决策一 · 票档从「百分比」改为「固定张数」

早期原型用百分比设票档（VIP 占 5%、GA 占 85%），数据模型很干净。但真实测试时发现：主办方不按百分比思考，他们按张数——「VIP 50 张、快通 50 张、其余 GA」。百分比模式逼用户每次都在脑子里做一层换算。改成固定张数后，系统输出和票务平台直接对齐，少了一层心智负担。

决策二 · 场馆租金按「星期」联动

同一个场馆，周六可能比工作日贵一倍。巡演排期有个常见策略：大城市放平日（反正卖得动、省场租），小城市放周末（观众只在周末出门）。系统选好场馆和日期后自动套用对应租金档并即时反映在 P&L 上——改档期，成本变化立刻可见。

决策三 · 所有自动填充值，用户都能改

这成了贯穿系统的设计原则。工具从供应商数据库拉默认值、自动计算，但从不锁死任何字段。真实世界里场馆会给特殊折扣、供应商会临时调价、PM 可能对某城更了解。每个自动值都能手动覆盖。这条原则也划定了系统边界：它负责「估算」——这个项目财务上能不能成；而「执行」——选供应商、谈价格、评质量——永远是 PM 的领域。

三、用 AI 驱动的开发

这个项目最不寻常的地方：没有工程师团队。一个 PM——我自己——用 AI 作为开发伙伴，从零搭起一个 2,400+ 行的可运行系统。

工具链与分工

核心开发由 Claude 完成（代码实现、架构设计、计算逻辑）；Hermes AI 负责数据层（300+ 场馆 Excel 转 JSON、映射表整理）。我的角色是：需求定义、业务逻辑验证、数据采集（打电话问场馆报价、向供应商要价格表）、用户测试（我本身就是目标用户）、优先级决策。工作方式是一轮轮紧密的反馈循环：我用真实数据测试 → 写反馈文档 → Claude 改代码 → 我再验证。

AI 替代不了的部分

这个过程让我看清 AI 的边界。它写代码很快，但它不知道「Livehouse 不买保险」这类行业知识；不知道某些场馆档期要提前三个月定；读不懂供应商报价里的隐含条款（含不含税？含不含搬运？）。AI 替代的是编码劳动，替代不了行业经验带来的判断力。

四、产品现状与成果

系统现已覆盖 13 个成本组、65 个成本项，内置 200+ 场馆（覆盖 33 城），支持自动成本联动、损益模拟、回本点分析、多城巡演汇总，并扩展出：三语界面（中 / 英 / 西）、币种切换（¥ / $ / €）、我方 Offer 测算引擎、实时 P&L、敏感性分析、一键导出 Deal Memo 与整页 PDF。准确性经 16 份真实巡演 P&L（Wren、Aria Vale、Jordan Reese、Mira Lune 等艺人）验证。

  • 提速：一个 8 城巡演预算从 2–3 天 → 约 2–3 小时。
  • 解锁新能力：10 分钟内对比三套场馆组合的利润差异——这在以前要花大半天重做预算，所以根本没人做。
  • 工程化迭代：从 v1.0 到 v3.8.86，90+ 个版本；最后阶段「一个问题修透再下一个」，每版用 golden master（demo 利润精确到分）守恒，保证大改不改坏数字。

五、反思与学习

以下为初稿，建议你按面试语气改写成第一人称叙事。

这个项目让我对产品管理最大的认识

产品经理的核心价值不在于「做出一个东西」，而在于把模糊的「想要什么」翻译成可验证的逻辑和验收标准。早期我只用描述性语言跟 AI 提需求，结果反复偏差——直到我开始写清楚每个字段的计算公式和边界条件，产出才稳定。这正是 PRD 的意义。

如果重来，我会改变什么

我会更早做可行性验证、更晚投入建设。预测系统的失败本可以在几天的数据体检里就预见，而不是花几周搭原型之后才发现。先证伪，再投入。

AI 如何改变了我作为 PM 的工作方式

它把我从「写不写得出来」的焦虑里解放出来，让我能把精力放回真正属于 PM 的地方：判断什么该做、定义清楚逻辑、守住数据的单一可信源。AI 协作的本质是「你定义逻辑、AI 执行落地」——你是产品负责人，不是甩需求的人。

差异化与壁垒

  • 中国成本结构原生适配：报批费按城市行政级别、安保按场馆费率、票务平台费率、签证类型、地面交通车型——这些是海外工具里根本不存在的字段。
  • 数据壁垒：200+ 场馆、16 份真实 P&L 沉淀出的成本参考区间，是靠实地采集和历史项目积累的，难以快速复制。
  • 场景纯粹：不做排期、不做履约、不做结算——只把「立项前算账」这一刀做到又快又准，反而避开了与全栈平台的正面竞争。
  • 零摩擦形态：单 HTML 文件、无后端、无登录，邮件 / 微信转发即可协作，完全贴合中国主办方的实际工作流。
一句话定位：给中国 Livehouse 主办方的「立项前 P&L 计算器」——几小时内算清一个巡演赚不赚钱，把精力省给真正需要判断力的地方。

Phase 1 聚焦 Livehouse 规模（800–2,000 人），帮主办方在 Offer 阶段几分钟内完成损益模拟、评估可行性。技术上：单 HTML 文件，无需后端、无需登录，浏览器打开即用，存取通过 JSON 文件下载 / 导入实现，每次保存生成独立版本文件。

项目起源与 Pivot

项目起点是一个更宏大的想法——票房预测系统。在用已知数据验证时发现预测与真实票房完全对不上，复盘后归因为三点：数据严重不足、与 AI 的协作只停在描述性语言、以及方向本身存疑（票房预测极难验证）。

这次 pivot 的核心洞察：系统的价值不在于预测不确定的事，而在于把确定的事做得足够快、足够准——让主办方把精力省给真正需要判断力的地方。

产品需求文档 PRD

Phase 1 · Livehouse ｜ 描述截至 v3.8.86 的已交付范围

一、产品背景

演出主办方在立项阶段需要快速判断一个项目是否值得推进，核心问题只有一个：这场演出能不能赚钱？但回答它要同时处理十几个成本模块（场租、制作、Backline、交通、酒店、签证、报批、营销、票务费率……），加上艺人 Guarantee 的货币换算、各档票价的上座率敏感性——手工估算容易出错，且难以快速迭代不同假设。

核心价值主张：准确性优先，速度是副产品。系统内嵌真实市场价格参考区间，不依赖用户自己估数字；系统提供数据与计算，不替用户做判断。

二、目标用户

  • 主要用户：演出行业项目经理——负责 Livehouse 级别国际艺人来华演出的前期立项预算，有一定经验但不具备资深制作人的成本积累。
  • 演示用户：求职 / 面试场景下展示 PM 作品集。

五、功能模块详述

Section 0 · 项目信息

项目名称、场馆级别、乐队人数、艺人经纪公司、汇率（全局，Header 可改）、票务平台手续费率（默认 4% 秀动）、预提所得税率 WHT（默认 10%）。

Section 1 · 演出规划

月历视图：点击日期弹窗填城市 / 场馆 / 容量；跨月巡演自动显示连续月份；日期含星期与日类型标签（演出日 / 行程日 / 媒体日 / 休息日 / 落地日 / 离境日）。

Section 2 · 票务设置

多档票价，每档独立设置档位名称、容量占比、票价、目标上座率、目标售出量。VIP Profit Split（可选）：对任意票档启用 Price Lift，自动计算艺人 VIP 收入并在损益中单列。可变成本细项：出票费 / 手环 / PRS / 慈善 / 取消险。

Section 3 · 演出成本

13 个成本组、65 细项，来源于真实巡演内部 P&L：场地费用、Backline / 制作、地面交通（按车型 + 多车）、酒店（按档次 / 合住）、机票、签证、文化报批许可、营销、票务运营、保险、VIP 服务成本、其他（版权费等）。每项显示历史参考区间（低 / 中位 / 高），可参考或手动覆盖；每行可标注权责归属（主办 / 艺人 / 分摊）。

Section 4 · 损益结果

核心 KPI 卡片（每场均值）：净票房、主办成本合计、净潜力、保底、艺人 VIP 收入、本场净收益、净收益占比、盈亏平衡上座率。所有计算结果带 ⓘ Tooltip，点击显示完整公式。

Section 5 · 汇总方案

① 我方 Offer 测算引擎（建议保底 = NPBO×30%，金额可编辑、联动评级；满场落袋 Walk-out 卡；利润保护垫 % 可编辑）；② 敏感性分析（60–100% 六档上座率）；③ 巡演 Tour Summary（含「主办收益 − 差旅 = 巡演净收益」对账行）；④ Offer 截止提醒（按报批 / 宣传天数倒推，颜色预警）。

六、系统级功能

Demo 模式

内嵌 8 城 Livehouse 巡演真实数据，全字段只读，橙色横幅标注；入口为落地页「查看演示案例」。

新手引导 Tour

按 6 个 Section 逐区 11 步引导，聚光灯高亮 + 气泡说明，支持 ESC / 点背景退出。

国际化 i18n

中 / 英 / 西三语（国旗下拉，默认中文）；币种三段选择器 ¥ / $ / €，默认随语言、可点击覆盖。

导出

JSON 存档；整页 PDF（封面 + 目录 + 页码）；一键 Deal Memo（含潜在奖金 / 落袋 Walk-out 列与合计）。

七、技术架构

  • 文件形态：单 HTML 文件，无外部依赖、无后端、浏览器直接打开。
  • 数据存储：本地 JSON 文件，不上传任何服务器。
  • 状态管理：纯 JS 对象（defaultState 工厂函数），无框架；单页滚动 + Intersection Observer 锚点高亮。
  • 选择理由：演出行业的真实场景是邮件附件、微信传文件、临时电脑演示——单文件最可靠，没有依赖失效风险。

八、有意不在 Phase 1 范围内

场馆推荐引擎、Settlement 模块、对外 P&L 生成（Buffer 模式）、多用户协作、Arena / Stadium 成本结构、票房区间预测——均为有意排除，详见产品路线图 Phase 2 / 3。
